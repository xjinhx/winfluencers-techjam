# Shopping Copilot — Conversational Search & Recommendation Agent

**TikTok TechJam 2026 · Track 4: Shopping Copilot — AI Conversational Search and Recommendations**

A multi-turn shopping agent that finds a hidden target product in a 50,000-item
Amazon clothing catalog, deciding on every turn whether to ask a clarifying
question or return a ranked list — and, when it does rank, doing it with a
40-feature scorer tuned against the organizer's own metric. No LLM call, no
network access, and no third-party dependency anywhere on the turn path.

All numbers below were re-measured directly against this checkout — the
unmodified `evaluator/local_evaluator.py`, all 200 public sessions, output not
edited — rather than copied forward from an earlier draft.

## What this project is

Traditional keyword search has no memory across turns and cannot tell an
open-ended browse from a high-intent purchase. This agent addresses both, and
does it without a language model: every decision on the turn path — routing,
retrieval, ranking, and whether to ask a question — is a small, deterministic,
tunable function, chosen because the organizer's rules warn that official
scoring may run with no network access and a graded submission has to return
the same answer twice.

**Per-turn pipeline:** parse utterance → update dialogue state → route intent
→ retrieve (lexical BM25 + character-n-gram dense, fused) → conjunctive
injection → score 40 features per candidate → rank → decide whether to hold
the list or ask.

### How this maps to the four pillars in the problem statement

| Pillar | What we built | Where it differs from the brief, and why |
|---|---|---|
| **I. Intent routing & hybrid pipeline** | A 4-feature, one-formula BUYING/BROWSING/UNCERTAIN router (`intent.py`); retrieval fuses five per-field BM25 indexes with a character-n-gram dense route via convex combination (`index.py`, `dense.py`, `fusion.py`) | "LLM Semantic Ranking" is replaced by a tuned **linear** ranker (`ranking.py`). Deliberate: an LLM reranker is order-sensitive (non-deterministic across identical inputs) and the rules permit disabling network access at scoring time — see D3 in `agent_architecture.md` |
| **II. Dialog strategy** | `ShoppingState` (`state.py`) accumulates slots across turns and treats an intent override as **decay, not erasure**; `ClarificationPolicy` (`clarify.py`) triggers a clarifying question only when the candidate pool is still large, the ranker isn't yet confident (NQC), and the question is worth more than another retrieval call (measured, not assumed, answer probability) | Matches the brief closely — this is the best-supported pillar |
| **III. Self-evolution / dynamic context programming** | A `profile_affinity` feature reads accumulated purchase history and preference tags into the ranker; all other weights are fit **offline** by coordinate ascent against the public set, not rewritten at runtime | We did **not** build a system that re-writes its own orchestration logic mid-session. `profile_affinity` measures at **+0.0010** in ablation — present, and honestly reported as close to inert. This is the pillar we address most partially |
| **IV. Evaluation matrix** | HR@10 (coverage), MRR (precision), MTTC (efficiency) — the organizer's own metrics, computed by the unmodified evaluator | Direct match by construction |

## Architecture

### 1. Retrieval — `index.py`, `dense.py`, `fusion.py`

Five **per-field** BM25 indexes (`title`, `features`, `categories`,
`description`, `store`) — never concatenated, because a term match in a
12-token title carries different weight than the same term in 400 words of
description. Each field has its own length-normalisation `b` (0.20 on `store`
up to 0.75 on `features`/`description`).

A character-4-gram similarity index runs alongside (`dense.py`) — not a neural
embedding, a deliberate trade against the no-network rule. It buys tolerance to
spelling/morphology drift ("camisole"/"cami", "Skechers"/"skecher"); it does
not buy semantic generalisation. Both routes are combined by **convex
combination** (`fusion_alpha = 0.78`, tuned), not reciprocal-rank fusion —
Bruch et al. (arXiv 2210.11934) find RRF sensitive to its parameters and
poorly generalising out-of-domain, versus convex combination which is
sample-efficient enough to tune on 200 sessions.

Query terms drawn from constraint spans are damped by measured catalog
document-frequency (`constraint_commonness_penalty = 0.3`) rather than a
hand-written stop-phrase list, so boilerplate the customer quotes verbatim
("Manmade sole; Platform measures...") doesn't pull in thousands of unrelated
competitors.

### 2. Conjunctive injection — `agent.py`

A retrieval-depth cutoff (`per_field_depth = 1000`, `candidate_depth = 200`)
can leave a genuinely matching product just outside the pool. Before ranking,
any product whose full text contains **every** currently-disclosed constraint
span verbatim is added to the candidate set regardless of its BM25 rank
(gated by `injection_min_spans = 2`, `injection_max_survivors = 200` so an
under-selective conjunction is skipped rather than flooding the pool).

### 3. Feature scoring — `features.py`, `ranking.py`

40 named features per candidate (`FEATURE_NAMES`, verified against the code):
retrieval scores (7), phrase/bigram overlap and coverage (4), the conjunctive
`span_all`/`span_coverage` signal (2), catalog priors — popularity, rating,
price/description/feature-count presence (5), six constraint dimensions
(gender, brand, category, price, material, colour) scored **three ways** —
satisfied / violated / unknown — as 18 separate columns, and four context
interactions including `profile_affinity` and `category_focus`.

`unknown` is a first-class, mildly-penalised column, never an exclusion — the
catalog is sparse in exactly the fields a shopping agent would want to filter
on (price null on 78.9% of rows, `Color` present on 4.9%, `Size` on 1.9%), so
anything that deletes a candidate on a missing field deletes the target.

Scoring is a weighted linear sum, with **intent-conditional** weights: `Ranker`
builds one `LinearModel` per routed intent, and a handful of features
(`fused`, `bm25_title`, `profile_affinity`, `category_focus`) may carry a
different weight for buying vs. browsing vs. uncertain, because `fused` is a
convex combination of signals that also enter the vector separately — double
counting it is worse on constraint-bearing (buying) turns than on browsing
turns, which have no constraints yet to drown.

### 4. Clarification policy — `clarify.py`

Three gates, all from EAR (Lei et al., WSDM 2020): ask only if the candidate
pool is still large (`ask_min_candidates = 12`), the ranker's own confidence —
Normalized Query Commitment, Shtok et al. 2009 — is still low
(`ask_max_confidence = 0.82`), and the expected information gain clears a
floor (`ask_min_info_gain = 0.05`), overridden by a hard turn budget or an
explicit customer request to be asked something.

Gain is **not** plain entropy. Entropy alone picks `category`/`brand` — they
partition the catalog beautifully, and this customer answers them **never**.
Gain is `P(answered) × uncertainty removed`, with `P(answered)` measured
directly from the 200 sessions (`python -m tools.measure_attribute_yield`,
re-run for this document):

| attribute | answer rate | mean new chars disclosed |
|---|---|---|
| feature | 0.915 | 50.9 |
| other | 0.950 | 48.3 |
| material | 0.725 | 28.3 |
| color | 0.245 | 15.0 |
| style | 0.090 | 12.7 |
| size | 0.045 | 7.5 |
| use_case | 0.015 | 2.0 |
| brand / budget / category | 0.000 | 0.0 |

A question the customer cannot answer wastes one of ten turns however well it
would have split the catalog.

### 5. Recommendation-timing gates — `agent.py`

The evaluator breaks the session loop on the **first** turn the target appears
in the returned top ten, so that rank is final — a weak early list forecloses
a better one later rather than merely missing it. Two gates hold the returned
list back until there is something to rank on, and they read different
signals:

- `recommend_min_spans = 1` — has the customer disclosed anything concrete yet?
- `min_recommend_confidence = 0.054` (NQC-based) — has the ranker's own score
  spread committed to a leader, or is the top of the list still noise?

Both are inert at `0.0`/off (verified: the codebase's own fold-validated
record shows this reproduces byte-identical to the un-gated build), and both
are on in the shipped config. This single change — asking the same questions,
just not showing a weak list while waiting — accounts for most of the distance
between the ablation table below (0.7641) and the live score (0.9429); see
`CLAUDE.md` for the fold-by-fold validation.

### 6. Correctness fixes with zero measured public-set effect, adopted anyway

Two catalog-wide audits (not visible in the 200-session sample, by
construction) found and fixed real defects: a gender-hierarchy bug where
`kids` was scored as a sibling of `boys`/`girls` rather than their parent,
penalising ~1% of the catalog against its own listing; and a brand-matching
false-positive rate of 94% on single-word "brand" extractions (`wash`, `sole`,
`hand` from "Machine Wash"/"Rubber sole" boilerplate), now gated by measured
catalog text-commonness rather than a hand list. Both are adopted for the
private 800-session set specifically because a public-set score of exactly
0.0 is the expected, correct result for a fix targeting rows the public
sample doesn't contain — see `CLAUDE.md`'s "What was found" log for the
full measurement.

### What we found in the data

**Targets are a popularity-biased subpopulation, and this matters for how you
should read the popularity feature.** Median `rating_number` on target
products is ~6,846 versus ~12 for a random catalog row (single-feature AUC
≈0.955). This is a property of how the benchmark was built — targets are
sampled from real purchases, and purchases concentrate on popular items — not
a claim about shopper psychology. We use it as a **soft, Bayesian-shrunk
prior, never a hard filter**: pruning to `rating_number ≥ 25` would keep 97.5%
of targets while cutting the catalog to 37.9%, tempting but wrong, because the
discarded 2.5% is an unrecoverable HR@10 loss. Ranking by popularity alone
scores far below the baseline (query-blind, returns the same few items to
everyone); the gain comes from combining it with relevance evidence, not from
either alone. **We say plainly that this is correct for this benchmark and
would be wrong for a production store**, which would starve its long tail
ranking this way.

**Structured attributes are mostly missing, so the constraint system is built
around that.** `details.Department` is the one attribute with real coverage
(87.2% direct, 98.3% after a title/category-path fallback) and is the
strongest single elimination signal in clothing. Everything else — colour,
material, size, brand — is sparse enough that a naive "filter on missing
field" strategy would silently discard targets; hence three-way
satisfied/violated/unknown scoring throughout.

## Component ablations

Each row disables exactly one component, measured on the full 200 sessions
against the **default-weight build** (before the recommendation-timing gates
and conjunctive injection described above — see `docs/ablations.md` for the
committed table, `python -m tools.ablate` to regenerate):

| component removed | HR@10 | MRR | MTTC | TechnicalScore | Δ |
|---|---|---|---|---|---|
| *full (default-weight) system* | 0.885 | 0.5535 | 3.23 | 0.7641 | — |
| clarification policy | 0.380 | 0.1858 | 7.45 | 0.3167 | **−0.4473** |
| candidate depth 200 → 20 | 0.830 | 0.5689 | 3.67 | 0.7323 | −0.0318 |
| popularity priors | 0.860 | 0.5371 | 3.50 | 0.7410 | −0.0230 |
| phrase / bigram evidence | 0.870 | 0.5443 | 3.40 | 0.7502 | −0.0139 |
| coverage + category focus | 0.880 | 0.5417 | 3.30 | 0.7565 | −0.0076 |
| constraint scoring | 0.885 | 0.5470 | 3.23 | 0.7620 | −0.0021 |
| dense route | 0.890 | 0.5366 | 3.16 | 0.7628 | −0.0013 |
| per-field weighting | 0.895 | 0.5295 | 3.08 | 0.7648 | +0.0007 |
| profile personalisation | 0.885 | 0.5575 | 3.23 | 0.7650 | +0.0010 |
| MMR diversity (added, shipped disabled) | 0.885 | 0.5539 | 3.23 | 0.7641 | +0.0000 |

Clarification dominates by an order of magnitude: a browsing session opens
with a category and no constraints, and if the agent never asks, no new
information arrives for the rest of the session. Everything above this table
(the recommendation-timing gates, `span_all`, conjunctive injection) is a
second layer built on top of this baseline — it is a real, distinct set of
gains, not double-counted in this ablation, and is documented with its own
fold-validated numbers in `CLAUDE.md`.

## Grounding in prior work

- **Fusion by convex combination, not reciprocal-rank fusion.** Bruch et al.
  (arXiv 2210.11934) — see §1 above.
- **Clarification gate from EAR** (Lei et al., WSDM 2020), with the RL policies
  that build on it (SCPR, arXiv 2007.00194; UNICORN, arXiv 2105.09710)
  deliberately *not* implemented, because they assume clean per-item attribute
  sets this catalog does not have.
- **Query performance prediction via NQC** (Shtok et al., 2009) as the
  recommender's own confidence signal, with no ground truth available at
  inference time.
- **Tree ensembles / feature engineering over model class for tabular data**
  (Grinsztajn et al., arXiv 2207.08815) — motivated treating features as the
  contribution over a learned reranker; a LightGBM `lambdarank` reranker was
  in fact built and tested and is not shipped (see Limitations).
- **Anchor-based conversational recommendation** (PSCon, arXiv 2502.13881) —
  the TechJam simulator is anchor-based (predefined intent slots/attributes),
  which is why slot-based routing rather than free-form NLU is the right
  abstraction here.

Requires Python 3.10+. **The agent uses only the Python standard library —
there is no install step**; `requirements.txt` is deliberately empty because
official scoring may run without network access.

```bash
git clone https://github.com/xjinhx/winfluencers-techjam
cd winfluencers-techjam
```

Download `catalog.jsonl.gz` from the participant kit release, decompress it,
and place it at `data/catalog.jsonl` (expected row count: 50,000):

gzip -dk catalog.jsonl.gz

## Limitations and honest caveats

**Tuned and measured on the 200 public sessions; the private 800 is the real
test.** Weights were fit by coordinate ascent with train/holdout splits
throughout (`stratified_halves`, seed 7), and every adopted change in
`CLAUDE.md` reports its held-out fold alongside its full-set number — but 200
sessions is a small set, single-run MRR standard error is ≈0.029, and a change
smaller than that cannot be verified here even when it is real.

**The popularity prior is benchmark-specific by construction**, and would be
the wrong feature to ship into a live store — see "What we found in the
data" above. We consider stating this a strength (it demonstrates
understanding the label-generation process) rather than a flaw to hide.

**No neural semantic route, no LLM reranker.** Both were deliberate scope
decisions for the no-network-access / determinism requirement, not oversights
— a character-n-gram index and a LightGBM `lambdarank` reranker were each
built and evaluated; the reranker measured a tie at best against held-out data
(seven attempts, see `CLAUDE.md`) and is not shipped.

**Self-evolution / dynamic context programming is the pillar we address most
partially.** As stated in the mapping table above, personalisation is one
feature (`profile_affinity`, ablation Δ +0.0010) rather than a
runtime-adaptive orchestration system.

**Remaining headroom is concentrated in MRR, not coverage.** With HR@10 at
1.000, further gain has to come from placing an already-found target higher,
not from finding more targets — `docs/pending.md` and `CLAUDE.md`'s
"Roadmap" section track this in detail, including which reranking approaches
were tried and rejected on held-out evidence.
